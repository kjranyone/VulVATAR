状態: 主要な変形経路の静的レビュー済み。再現実験・修正・新規ベンチは未実施。

## 1. 目的と問題設定

VulVATAR の目的は、RealSense による高品質な追跡と、物理演算を伴う自然な3D表現を、配信で安定して利用できる形で提供することである。最優先の利用条件は、頭と肩が主に見え、カメラが斜めに置かれ、手が常時デスク下にあるデスク配信である。

現在の問題は、個々の症状を改善すると別のアルゴリズムの挙動が悪化する変更を繰り返していることである。本計画では、各部分の設計が正しいことを前提にしたパラメータ調整より先に、アルゴリズム間の前提・責任・情報の意味を監査する。

中心仮説は「各部が別々の正しさを追っており、その接続を保証する設計契約が不足している」である。これは原因の確定ではない。代表的な退行を計測し、この仮説を支持・反証してから構造変更を決める。

成功とは、見た目の改善に加え、変更の影響を契約から説明でき、退行したときに破られた前提を特定できる状態である。

## 3. 確立する設計契約

### 3.1 推定と配信用の補完

次の三つを概念として区別し、データ構造への反映方法は監査後に決める。

1. センサが観測した情報。
2. 観測と事前から推定した人間の状態、およびその不確かさ。
3. 不可観測部分を含め、配信用に選択したアバターの姿勢。

「見えていない腕を自然に置く」ことを「腕を高精度に観測した」と解釈させない。予測や保持による安定を、データによる確信と混同しない。保持、休止姿勢への復帰、動作の補完を誰が決めるかを明示する。

### 3.2 境界ごとの契約項目

対象境界は、入力取得 → 観測生成 → 推定 → リターゲット → 物理 → 描画 → 外部出力とする。

| 項目 | 必須の定義 |
|---|---|
| 状態 | 人間・アバターのどちらを表すか、関節位置か回転か、基準姿勢 |
| 空間 | 座標系、左右・鏡映、単位、変換方向、身体スケールの意味 |
| 時間 | 取得時刻、推定対象時刻、予測時刻、有効期間、欠落・順序逆転の扱い |
| 情報源 | 実観測・予測・事前・補完の由来、他の観測との共有情報 |
| 不確かさ | σ・共分散・可視性・data-σそれぞれの意味と較正対象 |
| 権限 | 変更可能な自由度、最終決定者、競合時の優先順位 |
| 劣化と復帰 | 不可観測、追跡喪失、負荷制限、再観測時の状態遷移 |

特に、σが推定誤差・データ不足・表示用ブレンド量を無意識に兼用していないかを確認する。固定ステップの物理と可変周期の追跡・描画では、衝突対象と姿勢の時刻整合も契約に含める。

## 4. 実施段階と判定

### Phase A: 退行の因果監査と再現基盤

作業:

- 「Aを改善したらBが壊れた」代表例を3件選び、修正前後の差分・録画・設定・最悪区間を固定する。候補は追跡の安定性と動作忠実度、不可観測肢と復帰、姿勢変更と物理破綻とする。実例があるものを採用する。
- 現在のコミットに加え、未コミット差分・未追跡の実装ファイルも保存またはハッシュ化する。モデル、アバター、設定、GPU、ドライバ、ビルド条件、録画識別子を記録する。
- リプレイで録画の実内部パラメータと相対時刻を使用する。時刻の単位・クロック領域・単調性、欠落フレームを検証する。メタデータがない旧録画の名目条件は結果に明記し、実時刻評価と区別する。
- 境界ごとの入力・出力を対応するフレームと時刻で記録し、どの意味・前提が変化したかを追う。
- 一度の比較では一つの仮説を検証する。必要に応じて二つの機構の有無を組み合わせ、相互作用を測る。

成果物: 退行3件の因果レポート、再現用マニフェスト、固定評価セット、一括比較手順。

完了条件: 別の実行でも退行を再現でき、影響が初めて現れる境界を示せる。未確定の因果は未確定のまま明記する。

### Phase B: 契約と設計判断

作業:

- 第3節の契約表を実際の型・関数・所有スレッドに対応付ける。
- 共有深度情報の相関、観測数と実効情報量、モデル誤差、共分散と観測到達度の解釈を監査する。
- crop・可視性・対応付けのフィードバックを、初期誤差・遮蔽・再入場で検証する。
- 事前、手首保持、休止ブレンド、リターゲット、衝突が同じ自由度へ異なる要求を出す条件を整理する。
- 機構ごとに「維持」「責務移動」「統合」「削除」を、証拠と反証条件付きで決定する。

成果物: 境界契約、状態遷移、拘束の責任表、設計判断記録、依存順の実装バックログ。

完了条件: 不可観測部の扱い、最終姿勢の決定権、時間の整合、各種σの意味が一意に説明できる。退行3件を契約違反または明示されたトレードオフとして説明できる。

全面書き直しや別モデルへの交換は、この段階の結論に基づいて判断する。

### Phase C: 契約が成立する最小構成

作業:

- 頭・胴の追跡と、未観測腕の扱いを中心に、入力から最終アバターまで最小構成を成立させる。
- 同一入力で「推定リグ」「物理OFFのアバター」「物理ONのアバター」「最終出力」を比較できるようにする。
- 静止、首振り、胴ひねり、手の出入り、遮蔽、喪失・復帰を評価する。
- 変更対象の契約に対するテストと、エンドツーエンドの退行判定を組み合わせる。

成果物: 最小構成、比較レポート、契約を検証するテスト。

完了条件: デスク配信の主要条件で、安定性・忠実度・復帰・遅延の基準を同時に満たす。動作を抑圧して静止指標だけを良くした実装を合格にしない。

### Phase D: 追跡範囲と物理の拡張

作業:

- 手、表情、体格差への対応を追加し、頭・胴の品質を維持する。
- 曲げ拘束について、目標角への誤差減少、両方向の補正、退化配置、固定点を検証してCPU参照を修正する。その後にGPUへ展開する。
- 髪・布を固定姿勢と既知モーションで個別評価してから、追跡入力へ接続する。
- スプリング、布、クリアランス、身体衝突の役割と実行順を契約に合わせる。
- 異なる描画fps、ゼロsubstep、長いフレーム、追跡復帰での挙動を比較する。

成果物: 拡張ごとの回帰結果、物理の参照ケース、CPU/GPU比較。

完了条件: 新しい機能が既存契約を守り、発散・持続貫通・不自然な伸長を生まない。CPU/GPUで共有する誤りを見逃さないよう、同値性だけでなく物理的な正しさを判定する。

### Phase E: 映像品質と運用保証

作業:

- 固定カメラ・照明・姿勢で、材質、法線、影、輪郭、透明髪、アンチエイリアスを評価する。
- プレビューとOBS等の最終出力で、色、α、解像感、フレーム周期を比較する。
- 入力取得から出力までの遅延分布と待ち時間を測る。負荷制御時は、古い深度や姿勢が新しいデータとして扱われないことも確認する。
- 1時間から4時間へ連続運転を伸ばし、ロード、追跡開始・停止・再開、出力再接続を検証する。

成果物: 見た目の基準画像・動画、遅延レポート、長時間試験結果、対応する運用条件。

完了条件: 指定したPC・アバター・解像度で品質と安定性を満たし、負荷制限時の挙動を説明できる。

遅延の計測自体はPhase Aから行う。最終段階まで性能問題を持ち越さない。

## 5. 評価セットと品質判定

### 5.1 入力の構成

- 主評価: デスク配信。頭と肩のみ、斜めカメラ、手が机下、部分的な手の出入り。
- 動作評価: 正面のwave、palms、namaste、首振り、胴ひねり。
- 回復評価: 顔の遮蔽、画面外への移動と再入場、深度欠落。
- 物理評価: 固定姿勢、既知の回転・加減速、衝突、複数アバター。
- 映像評価: 固定条件の静止画と動作動画、透明背景での合成。

既存録画を優先し、不足条件だけ追加収録する。調整用と未使用の評価用をセッション単位で分ける。合成GTは既知誤差の検証に使い、実録画での品質保証と併用する。

### 5.2 初期目標案

以下は達成済みの値ではない。Phase Aで基準値、測定定義、対象PC、必要なラベルを揃え、Phase C着手前に採否・修正理由を記録する。

| 対象 | 初期目標・判定方法 |
|---|---|
| 静止時の頭・胴 | 静止区間のyaw標準偏差2°以下。意図した動作区間と分離する |
| 手首・rootの破綻 | 静止・遮蔽区間の不要な15cm超ジャンプ0件。小さい跳びも分位点と最大値で記録する |
| 未観測手 | 未観測ラベルに対する誤追跡率・data-σ dutyと、最終アバターの不要移動量を併記する |
| 動作忠実度 | GTで十分な振幅のある主要回転・移動のゲイン0.8〜1.2。符号と別部位への誤連動も確認する |
| 復帰 | 明瞭な再観測から0.5秒以内を目標とし、復帰時の跳びも採点する |
| 不確かさ | 既知誤差と予測した不確かさの対応、不可観測時と再観測時の挙動を評価する |
| 物理 | NaN・発散0件。貫通は深さ・継続時間・画面上の見え方、伸長は比率で判定する |
| 実時間性能 | 対象PCで1080p・60fps出力、入力から出力までの遅延p95が100ms以下を初期目標とする |
| 安定運用 | 1時間、続いて4時間でクラッシュ・停止・継続的メモリ増加なし。ドロップ数も記録する |

各数値には評価区間、座標系、単位、サンプル数を添える。可視性や復帰の採点には、人手またはGTの基準を使い、推定器自身の判定だけを正解にしない。

平均値だけで合否を決めず、最悪区間・p95・最大値・短い比較動画を残す。忠実度、安定性、遅延のいずれかが悪化した場合は、その交換条件が事前の許容範囲内かで判断する。

## 6. 実装と回帰防止の運用

変更ごとに以下を一組として残す。

1. 再現入力と問題区間。
2. 破られている契約、または検証する設計仮説。
3. 変更内容と影響すると予測する範囲。
4. 修正前後の数値・映像と、未使用評価セットの結果。
5. 合格・不合格の判定、残る制約。

腕・顔の変更では、正面系とデスク系の両方のFusionリプレイを必須とする。単体テストだけで完成扱いにせず、また全体指標だけで境界の意味の破壊を見逃さない。

症状に合わせたゲートの追加は、どの残差・事前・σが誤っているかを計測してから判断する。新しい機構を加えるときは、既存の保持・補完・拘束と責務が重ならないかを確認する。

現行仕様は既存のAs-Is文書へ反映し、実験履歴と設計判断を混ぜない。本書は計画と完了条件を管理する。

## 9. 画像報告を起点にしたコードレビュー

### 9.1 調査範囲と証拠の限界

ユーザー画像では胸元・裾に三角形状の崩れがあり、胴体中央で衣服と肌の不自然な重なりが見える。画像だけでは、実際の穴、貫通、頂点の離散、材質・法線の問題を確定できない。追跡が原因、布だけが原因という前提を置かない。

画像報告直後のlive debugの読み取りでは、`avatars_loaded=1`、`paused=false`、`tracking_enabled=true`で、`frame_count`は70349から71230へ進行し、`sim_substeps`はそれぞれ2と5だった。`debug_avatar_extra.json`では`cloth_deforms=1`、`cloth_targets=[12]`だった。これらは画像と同期していない別時刻の読み取りであり、破綻フレームの状態として扱わない。JSONの原本はその時点では保存していないため、再検証では必ず保存する。

### 9.2 実装上の変形順序

`src/app/render.rs`の`run_frame`相当の処理では、次の順に状態が更新される。

1. フレーム共通のsimulation clockを進め、substep数を決定する。
2. `build_base_pose`で基準姿勢を構築し、`apply_rig_pose`で追跡を反映する。
3. `compute_global_pose`を実行する。
4. `debug_avatar.json`と衣服用の追加デバッグを出力する。
5. スプリング・CPU布等の物理を実行し、最終skinning matricesを構築する。
6. レンダー入力を作り、GPU側で布を計算する。
7. `transform_cs`で通常メッシュにはDQSを適用する。布対象では布の位置を採用し、スキニングを迂回する。
8. 同じシェーダ内でclearance、続いてcontainmentスロットの補正を適用し、最終VBOへ書く。
9. GPU cloth readbackは布SSBOをCPUへ戻す。最終補正後のVBOではない。

主な参照: `src/app/render.rs`の`apply_rig_pose`呼出し・`SimulationStepOptions`・`apply_cloth_readback`、`src/renderer/compute_prepass.rs`の`record_compute_prepass_planned`、`src/renderer/pipeline.rs`の`transform_cs`。

この順序から、現在のデバッグ骨格やCPUのskirt bboxが正常でも、物理後・GPU変形後の正常性は保証されない。また、布SSBOが正常でも最終描画頂点の正常性は保証されない。

### 9.3 レビュー項目

優先度P1は原因の確定を意味しない。品質判断を誤らせる契約不一致、または再現確認を優先する実装上の問題を表す。各項目は修正前に最小実験で確認する。

#### R1 / P1: GPUの衝突実行頻度がCPUと異なる

**コードで確認:** `src/renderer/compute_prepass.rs`の`record_compute_prepass_planned`では、`for _ in 0..cloth.substeps`（レビュー時954行付近）が積分と距離拘束を囲み、self-collision（1064行付近）とcapsule collision（1113行付近）はそのループの外にある。コメントは「once per substep」としている。一方、CPUの`cloth_solver::step_cloth`は一回ごとに衝突まで処理され、アプリからsubstep回呼ばれる。

**影響:** 複数substep時にGPUだけ衝突を中間で解かず、0 substep時にも衝突dispatchへ到達し得る。衝突が有効な条件で、描画周期によってCPU/GPUの挙動が変わる構造である。今回の画像への寄与は未測定。

**実験・完了条件:** ピンと球／カプセルを持つ小さな布で0・1・2・5 substepを実行し、実dispatch数、貫通深さ、最大変位を比較する。契約に合わせて衝突の位置を決め、GPU実行経路そのものを検証する。数式をコピーした単体テストだけで完了しない。

#### R2 / P1: 最終頂点と物理状態の間で拘束が共有されていない

**コードで確認:** `transform_cs`は布の`world_pos`を読み出した後にもclearanceとcontainmentを適用する（`pipeline.rs`1383、1463〜1509行付近）。出力先は`out_v`であり、cloth位置・前位置SSBOへの書き戻しはない。法線はこの最終位置補正後には再計算されない。

**影響:** 布の距離拘束・衝突が成立した位置と、画面に出る位置が異なる。補正量が大きい場合の伸長、面反転、法線の不整合を物理側の指標では検出できない。描画上の小さな補正として成立する可能性はあるが、許容変位や変形品質の契約が必要。

**実験・完了条件:** 同じフレームで布直後、clearance直後、containment直後の頂点を取得し、辺長比・三角形面積・隣接面の異常・補正量・法線との角度差を記録する。診断用の中間バッファが必要。恒久対策は「補正を物理拘束に統合する」か「描画補正を許容範囲に限定し異常を検出する」等を比較し、単に描画位置をVerletへ戻して速度を壊さない。

#### R3 / P1: containment参照面の時刻がバッファ更新順に依存する

**コードで確認:** `prepare_compute_prepass`はclearanceのみを依存グラフの辺にし、containmentは除外する（`compute_prepass.rs`81〜96行付近）。`materialize_parent_vbo`は親の同じ`transformed_vbo`を参照する。明示的な前フレーム専用バッファではない。

**影響:** 親が後で実行される場合は前回の面を読むが、先に実行済みなら今回の面を読む。コメントの「previous-frame」はデータ構造で保証されない。Phase 3のcross-region clearanceもこのスロットを使うため、名称だけでは依存関係を判断できない。初回の数値範囲チェックもフレームの有効性を保証しない。

**実験・完了条件:** 相互依存する衣服と独立したcross-regionケースで、primitive列挙順・初回・再ロード・急な姿勢変化を比較する。親の生成frame IDを記録する。補正前の全メッシュを先に生成する二段構成、または明示的な世代付き履歴バッファ等を比較し、循環拘束の解法と読む時刻を仕様化する。依存辺を単純追加してcycle fallbackを誘発する修正は避ける。

#### R4 / P1: readbackの配送先がprimitive IDだけで決まる

**コードで確認:** `ClothReadback`には`mesh_id`と`primitive_id`があるが、`apply_cloth_readback`は全アバターを走査し、GPU backendと`target_primitive_id`だけで適用する（`src/app/render.rs`631行付近）。`mesh_id`を使わず、instance IDと世代もない。`frame_input.rs`はprimitive IDをアバター内で一意と説明している。

**影響:** 同じprimitive IDを持つ複数アバターに別個体のreadbackを適用し得る。CPU側の表示・バックエンド切替等が誤った状態を利用する可能性がある。画像時の読み取りは1体なので、この問題を当該画像の原因とはしない。

**実験・完了条件:** 同じアセットを2体、異なる姿勢で動かし、配送先と座標を確認する。`instance + primitive + generation + frame`等の識別契約を確立し、古いreadback、削除・再追加、並べ替えを検証する。rendererのtransform cacheも`(mesh_id, primitive_id)`をキーにしているため、同一アセット複数instanceの状態分離を併せて監査する。

#### R5 / P1: 現在の衣服プローブは最終変形の検証になっていない

**コードで確認:** `debug_avatar_extra`の出力は物理処理より前にある。skirt bboxは`Circle.056`を名前で選び、CPUで重み付き行列変換を計算している。GPU通常経路はDQSで、布・clearanceも後段にある。

**影響:** bboxが正常という証拠から「頂点は正常で描画だけの問題」と判定すると誤る。単一bboxは三角形単位の崩れも隠す。

**実験・完了条件:** 診断にstage、instance、primitive、frame、pose時刻を付ける。物理前／後、GPU布後、最終VBOを明示し、問題の胸元・裾のprimitiveを材質とIDで特定する。既存プローブは名称と説明を実際の測定内容へ直す。

#### R6 / P1調査: auto-clothの疑似weldは同一位置の維持を保証しない

**コードで確認:** `auto_cloth.rs`の`build_cloth_for_prim`は位置を量子化してweld groupを作るが、粒子は描画頂点ごとのまま維持する。隣接weld groupの重複頂点をround-robinで距離拘束へ接続する（294〜377行付近）。同じweld groupの粒子を一つにする実装ではない。

**未検証の仮説:** UV・法線の継ぎ目で同位置だった粒子が、異なる近傍拘束や衝突により離れ、三角形の隙間を作る可能性がある。一方、位置だけのweldは、本来別の重なった衣服面を結び付ける可能性もある。画像からの断定は禁止。

**実験・完了条件:** 分割頂点を持つ小さな平面と、同位置の別レイヤーを用意し、group内距離・連結成分・拘束次数・質量の重複を検証する。物理粒子と描画頂点の対応を分離し、物理上連続すべき頂点だけを共有する設計を第一候補として評価する。ばねの硬さだけで継ぎ目を抑え込まない。

#### R7 / P2: 曲げ拘束は角度モデルから確認する

既知の逆方向問題に加え、実装は3点の二本の辺の角度を扱う一方、コメントはdihedralと呼ぶ。共有辺を持つ二つの三角形の曲げを表す契約と同一かを確認する。既存モデルを正しい参照と決めてGPUへコピーしない。auto-clothは曲げ拘束を生成しないため、この既知問題だけを今回の崩れの説明に使わない。

#### R8 / P2調査: DQSと入力変換の前提を検証する

`transform_cs`は行列の3×3部分からquaternionを作り、回転と並進で位置を再構成する。CPUプローブやauto-cloth初期位置は行列による重み付き変換を使用する。非一様scale・鏡映・shearを入力行列が含み得るか、インポート段階で除去されるかは今回未確認。

FBX/VRMのrest姿勢、単一骨、複数骨、scaleを持つ最小素材でCPU参照とGPUを比較する。DQS/LBSの意図した差と、入力条件違反を区別する。画像の胸元が布対象外でも崩れる場合の優先調査先とする。

## 10. 引き継ぎ先の具体的な実施順

### 最初の作業: 現行状態と破綻入力の固定

1. `git status`とレビュー対象差分を確認する。進行中の変更を上書きせず、必要なら差分込みの独立した検証checkoutを用意する。ユーザーの変更を解除・復元しない。
2. アプリの実行ファイル・起動時刻・設定・アセットhashを確認する。ディスクの新バイナリと稼働中プロセスは一致するとは限らない。
3. live channelからGUI、追跡、物理前後の状態を保存する。センサ入力が必要ならsequence recorderを使い、ドロップした録画を評価に使わない。
4. 胸元・裾のprimitive ID、cloth対象、clearance親、containment親、spring対象骨を対応表にする。画面上の位置からIDを推測しない。
5. 同じ追跡出力または固定した骨変換を繰り返し投入できる診断経路を作る。Fusion再推論だけでは下流の切り分けにならない。物理も同じ初期状態から開始する。

### 最初の実験: 機構の単独・組合せ評価

以下の「無効化」は診断構成として実装・確認するもので、既存環境変数がすべて存在するという意味ではない。各実行で初期状態をリセットし、実際の有効フラグを結果に記録する。

### 修正順と採否

1. **診断の意味を正す（R5）。** 最終頂点を測れない状態で修正の効果を判断しない。
2. **実行契約を正す（R1）。** substep頻度と0-stepの仕様を固定する。R4は複数instanceの再現を独立して行い、配送契約を修正する。
3. **最初に崩れる段階を修正する。** E1ならR8とインポート、E3ならR6と布、E4〜E7ならR2/R3を優先する。すべてを同時に変更しない。
4. **最終頂点の所有権を設計判断として残す。** 物理が所有する位置と描画補正の範囲、参照面の時刻、拘束の競合時の方針を確定する。
5. **追跡の設計監査へ接続する。** 下流を固定したうえでPhase A〜Cの観測・σ・フィードバックを検証し、下流の破綻を追跡の調整で隠さない。
